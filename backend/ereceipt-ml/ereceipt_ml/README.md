# E-баримт унших локал ML (CRF-суурьтай)

Энэ бол "LLM шиг" контекстээр ойлгодог, гэхдээ 100% локал, хурдан ажилладаг
загвар. `RandomForest`-ийн оронд **CRF (Conditional Random Field)** ашигласан —
энэ нь мөр/баримт даяар токенуудын **дараалал**-ыг харгалзан "энэ тоо яагаад
ДДТД, тэр тоо яагаад дүн вэ" гэдгийг сурдаг тул илүү зөв ажиллана.

## Яагаад CRF, яагаад RandomForest биш?

Танай хуучин загвар мөр бүрийг тусад нь ангилдаг байсан тул:
- ХМ Наадам шиг баримт дээр **олон ДДТД** байхад алийг нь сонгохоо мэдэхгүй байсан.
- Урт дугаар 2 мөрөнд нугалагдвал бүрэн олдохгүй байсан.

CRF нь өмнөх/дараагийн мөрийн **keyword context**-ийг (жишээ нь "ДДТД",
"ДАТА", "Төлөх", "Нийт") болон тухайн токены байрлал, урт зэргийг нэгтгэн
харж шийддэг тул танай 4 бодит баримт дээр **DDTD болон Дүн хоёуланг нь
100% зөв** олсон (`infer.py`-г ажиллуулж шалгасан).

## Файлын бүтэц

| Файл | Зорилго |
|---|---|
| `templates.py` | Танай 4 бодит баримт (ТЭС, Глобал молл, ХМ Наадам, GS25) дээр үндэслэсэн загварууд |
| `generate_data.py` | Синтетик сургалтын дата үүсгэнэ (мөнгөн дүн, ДДТД, огноо санамсаргүй) + бодит OCR алдаа (typo), мөр нугарах зэргийг дуурайлгана |
| `features_crf.py` | Токен түвшний шинж чанар гаргах логик (keyword context, digit length, position гэх мэт) |
| `train_crf.py` | CRF модель сургаад `crf_model.pkl`-д хадгална |
| `infer.py` | Сурсан моделиор шинэ баримт задлах (`parse_with_crf`) — олон мөрөнд хуваагдсан ДДТД-г дахин угсарна |
| `main.py` | Танай FastAPI сервер — CRF-г үндсэн парсер болгож, regex-ийг fallback болгосон, `/feedback`-ээс автоматаар дахин сурна |

## Хэрхэн ажиллуулах

```bash
pip install -r requirements.txt
python3 train_crf.py        # эхний удаад модель сургана (crf_model.pkl үүснэ)
uvicorn main:app --reload   # серверийг асаана
```

## Онлайн сургалт (feedback loop)

Хэрэглэгч алдаатай уншсан утгыг зассан үед `/feedback` endpoint рүү илгээнэ:

```json
{
  "raw_text": "...",
  "corrected_ddtd": "0511012658610010969800158100 45937",
  "corrected_amount": "2040"
}
```

Энэ нь `receipt_data.db`-д хадгалагдаад, дэвсгэрт (background task) синтетик
дататай хамт CRF-ийг дахин сургана. Бодит жишээг 5 дахин жинтэй болгосон
(`real_samples * 5`) тул цөөхөн бодит жишээ ч гэсэн загварт мэдэгдэхүйц нөлөө
үзүүлнэ.

## Хуучирсан / бүдгэрсэн / Vertical зурагны талаар

Танай 2 нэмэлт бодит зураг (нэг нь хуучирсан, нэг нь маш бүдгэрсэн) дээр
шалгасны дүнд:

- **Vertical (босоо) орчил өөрөө асуудал биш.** Chек нарийн, урт цаас тул
  босоо зураг бол хэвийн зүйл — OCR мөр бүрийг хэвтээгээр уншдаг тул зураг
  өөрөө босоо байх нь саад биш.
- **Хуучирсан/бүдгэрсэн цаас бол жинхэнэ асуудал.** Энэ CRF загварын биш,
  **OCR (`pytesseract`)-ийн текст задлах чанарын** асуудал — модель зөвхөн
  OCR-ээс гарсан текстийг л харна.
- Шалгалтын явцад 2 бодит алдаа олж, засав:
  1. **Cyrillic/Latin андуурал**: OCR заримдаа "ДДТД"/"ДАТА" гэдгийг "DDTD"/"DATA"
     (Latin үсгээр) уншдаг тул keyword context алдаж байсныг `features_crf.py`
     дэх `normalize_ocr_confusables()` функцээр засав.
  2. **Аравтын бутархай (.00) дүнг буруу уншдаг байсан**: "39,138.**00**" гэсэн
     дүнг өмнө нь "3,913,800" (100 дахин ихэсгэсэн) гэж буруу тайлж байсныг
     `clean_amount_digits()` функцээр засав.
- `main.py`-д зурган баримтыг **автоматаар сайжруулж** (grayscale, contrast
  stretch, sharpen, томруулах) OCR-д илгээх, мөн raw/enhanced хоёр хувилбарыг
  аль алиныг нь туршиж хамгийн бүрэн үр дүнг сонгох логик нэмсэн.
- **Хязгаарлалт**: маш их муудсан/бүдгэрсэн (жишээ нь урт хугацаанд халаасанд
  байсан термал цаас) баримт дээр OCR-ийн ямар ч сайжруулалт хангалтгүй байж
  болно — энэ тохиолдолд хэрэглэгчид гараар засах (`/feedback` endpoint)
  боломжийг үргэлж харуулах нь зөв шийдэл.

## Хэвтээ (Horizontal) зурган баримт

Хэрэглэгч утсаа хэвтээгээр барьж авсан баримтын зураг өмнө нь **юу ч уншигдахгүй**
байсан (OCR `--psm 4` зөвхөн босоо чиглэлийн текстийг хайдаг). Одоо `main.py`
дотор **автомат чиг баримжаа засал** нэмэгдсэн:

```python
def auto_rotate(img):
    """Tesseract-ийн OSD ашиглан 90°/180°/270° эргэлтийг таньж зассана."""
```

Энэ нь `pytesseract.image_to_osd()`-ийг ашиглан зургийг OCR-д илгээхийн өмнө
шалгаж, шаардлагатай бол эргүүлдэг. Тестээр баталгаажуулсан:
- Хэвтээ зураг (90° эргэсэн) → `Rotate: 270` зөв илрүүлж, буцаан засав.
- Заслын дараа OCR дахин ажиллаж эхэлж, ДДТД/дүн олдох боломжтой болов.

**Санамж:** OSD нь зурган дээрх текст **хангалттай тод байх шаардлагатай**
(маш бүдгэрсэн зурган дээр чиг баримжааг ч андуурч болно) — тиймээс энэ
функц ч гэсэн эх зурган чанараас шалтгаална.

## Аравтын бутархай (.00 vs .50) зөв ялгах

`'.'` тэмдэгтийг **аравтын бутархай** гэдгийг зөв ойлгодог болгосон
(`normalize_amount()` функц, `features_crf.py`):

| Оролт | Гаралт | Тайлбар |
|---|---|---|
| `39,939.00` | `39939` | Бутархай бүхэлдээ 0 тул хасна |
| `39,939.50` | `39939.50` | Бутархай 0-ээс их тул хадгална |
| `2,040` | `2040` | Бутархайгүй бол өөрчлөгдөхгүй |

Сургалтын синтетик датанд ч гэсэн 3 тохиолдлыг (бутархайгүй / `.00` / бодит
`.XX`) санамсаргүй холино тул CRF загвар аль ч тохиолдолд зөв ялгахыг сурсан.

## Хязгаарлалт ба цаашдын сайжруулалт

- Одоогийн synthetic дата зөвхөн 4 загвар дээр суурилсан тул **огт өөр
  байгууллагын** баримт (жишээ нь өөр дэлгүүрийн систем) дээр анх удаа
  бага зэрэг регекс fallback руу унах магадлалтай — гэхдээ `/feedback`-ээр
  бодит жишээ нэмэгдэх тусам сайжирна.
- Хэрэв танд GPU байгаа бол `features_crf.py`-г NER-transformer рүү
  шилжүүлж болно (өмнөх ярианд дурдсан 3-р шат) — гэхдээ CPU дээр CRF
  хурдан бөгөөд энэ хэмжээний dataset-д хангалттай сайн үр дүн өгч байна.
